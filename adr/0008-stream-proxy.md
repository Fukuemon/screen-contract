# ADR-0008: ライブ映像は Workflow Server 経由の Proxy で配信する

## Status

承認

## Context

agent-browser は、ライブ映像（JPEG のフレーム）と入力の転送を WebSocket で提供する。  
Web UI がどこを通してこのストリームに接続するかを決める必要がある。

- MVP はローカルでの実行を前提にする。
  - 出典: [context/operations.md の Environments](../context/operations.md#environments)
- 将来のリモートでの利用を見据えた接続の構成が要る。

## Decision

- Web UI は Workflow Server の単一のエンドポイントにだけ接続し、server が agent-browser のストリームを中継（Proxy）する。
  - 映像のフレームの配信と、操作モードのときの入力の転送（逆向き）を、同じ接続で行う。
- agent-browser のポートは外へ公開せず、Workflow Server だけが接続する。
- 逆向きの入力の転送は、素通しにしない。
  - server の側で、対象の run が `paused` で、かつ操作モードであることを確かめてから中継する。
  - 条件を満たさない入力は破棄する。
  - 破棄したことはイベントとして残す。知らせずに捨てると、UI の側の不具合と、迂回の試みを区別できない。

入力の転送を server で確かめる理由は次のとおり。  
「再生中は入力を受け付けない」という規則は、Web UI が守るだけでは規則ではなく、画面の都合にすぎない。  
認証を通したクライアントは Proxy へ直接フレームを送れるため、client の側の制御は迂回できる。  
迂回されると、実行中の run の途中でページの状態が変わり、Expectation の評価が実際の操作と噛み合わなくなる。  
冪等実行と巻き戻しの前提が崩れる。

接続の構成と、中継する条件は [Web UI の Design Doc](../apps/web/DesignDoc.md#stream-proxy-の接続構成) にある。

## Considered Options

| 選択肢                                           | 強み                                                                                                                                                                                  | 弱み                                                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **採用:** Workflow Server が中継する（Proxy）    | 接続先が 1 つにそろい、認可、CORS、ポートの公開の問題を server に集められる。実行のイベントと同じ接続を通り、UI の実装が単純になる。実行の基盤を差し替えても、UI の接続先は変わらない | 中継の 1 ホップ分の遅延と、サーバーの負荷が乗る                                                                     |
| agent-browser へ直接接続する                     | ホップが 1 つ減り、遅延が小さい                                                                                                                                                       | 認証のないポートの公開と、接続先の分散（UI が実行の基盤のポートを知る）が残る。リモートにした時点で構成の変更が要る |
| ハイブリッド（ローカルは直接、リモートは Proxy） | —                                                                                                                                                                                     | 接続の構成が 2 系統になり、検証のコストが倍になる。ローカルでの利得が小さい                                         |

ローカルでの利用での遅延の差は中継の 1 回分であり、体験を左右する規模ではないと判断した。

## Consequences

### Positive

- 接続先が 1 つにそろい、認可、CORS、ポートの公開の問題を server に集められる。
  - 実行のイベントと同じ接続を通り、UI の実装が単純になる。
- 実行の基盤を差し替えても（Browser Port の別の実装）、UI の接続先は変わらない。

### Negative

- 中継の 1 ホップ分の遅延と、サーバーの負荷が乗る。
  - フレームの転送はバイト列の中継であり、実害は小さい見込み。
