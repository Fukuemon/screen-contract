# ADR-0016: agent interface に MCP と App Server 型 JSON-RPC の両方を採用する

## Status

承認

## Context

AI エージェントが本システムを操作するときのプロトコルを決める必要がある。

AI エージェント（Claude Code、Codex など）が人間と同じ use case を操作できることが、成功の条件である。  
出典: [PRD の Success Metrics](../PRD.md#success-metrics)

MCP は、汎用のエージェントをつなぐ標準の手段である。  
ただし、stateless になった現行の仕様では、サーバーからの任意の push が廃止された。  
そのため、実行イベントを低い遅延で配信するには、ポーリング（Tasks 拡張と、カーソルを付けたイベントの取得）しか使えない。

常駐し、低い遅延が要る統合（エディタの拡張など）には、双方向のストリームでサーバーが push できる手段が別に要る。

人間が起点の提案依頼も、pull 型のキューで受ける。  
エージェントが依頼を取りに来るまでの遅延は、そのまま利用者の待ち時間になる。  
遅延の特性は、プロトコルによって異なる。  
ADR-0020: [人間起点の提案依頼を pull 型キューで実現する](0020-suggestion-pull-queue.md)

## Decision

- MCP server と App Server 型 JSON-RPC の両方を提供する。
- 両方のプロトコルは、同じ tool の語彙と同じ JSON Schema を共有する。
  - agent モジュールの中の共通のマッピング層が、app の use case へ 1 対 1 で変換する。
  - プロトコルに固有の処理（通知とタスクの形式）だけを、各サーバーの実装に置く。
- 汎用のエージェントからの操作には MCP を、常駐と低い遅延が要る統合には JSON-RPC を使う。
- 提案依頼の取得（`suggestion.list`）は、App Server 型 JSON-RPC ではロングポーリングで待たせる。
  - MCP の側では、依頼のリストをリソースとして購読させ、通知を合図に取りに来させる。
  - 購読を張らないクライアントでは、ポーリングの間隔がそのまま遅延になる。
  - ADR-0020: [人間起点の提案依頼を pull 型キューで実現する](0020-suggestion-pull-queue.md)

プロトコルごとの対応は [AI エージェント操作の Design Doc](../packages/agent/DesignDoc.md#プロトコルの対応) にある。

## Considered Options

| 選択肢                                                                         | 強み                                                                                                                                                                 | 弱み                                                                                                                             |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** MCP と App Server 型 JSON-RPC の両方を、同じ語彙と Schema で提供する | 汎用のエージェント（設定 1 行）と常駐の統合（低い遅延の push）の、どちらの導入の手段も閉ざさない。語彙と Schema を共有するため、プロトコルの間で機能の差が生まれない | 2 つのサーバーの実装を保守する必要がある                                                                                         |
| MCP のみ                                                                       | 汎用のエージェントの導入が容易                                                                                                                                       | 現行の仕様の push の制約により、常駐の統合がライブにイベントを受け取れない。提案依頼の取得にも、ポーリングの間隔の分の遅延が残る |
| App Server 型 JSON-RPC のみ                                                    | 低い遅延を満たす                                                                                                                                                     | エージェントごとに専用のクライアントの実装が要り、設定 1 行で接続できる MCP の導入の容易さを失う                                 |
| REST API を直接使う                                                            | —                                                                                                                                                                    | エージェントへ tool を公開する標準の形がなく、エージェントごとに tool の定義を作り込むことになる                                 |

## Consequences

### Positive

- 汎用のエージェント（設定 1 行）と常駐の統合（低い遅延の push）の、どちらの導入の手段も閉ざさない。
- 語彙と Schema を共有するため、プロトコルの間で機能の差が生まれない。
  - 差は、配信と取得の遅延の特性だけに限られる。
- 両方のプロトコルを併用する理由が、実行イベントの配信に加えて、提案依頼の取得にも及ぶ。
  - 片方だけでは、実行イベントの配信と提案依頼の取得の両方で遅延が残る。

### Negative

- 2 つのサーバーの実装を保守する必要がある。
  - 共通のマッピング層へ集めることで、差を tool の定義の複製ではなく、配信の方式に限る。
