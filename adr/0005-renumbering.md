# ADR-0005: 構成番号は状態単位で採番し、badges リストを基準に読み順の再採番で管理する

## Status

承認

## Context

構成番号の管理では、次の 3 つを決める必要がある。

- どの範囲で番号を振るか（スコープ）
- 削除と追加で、番号がどう動くか
- 番号を、DSL と成果物のどちらが持つか

決定に関わる事実は次のとおり。

- 番号を固定して安定させる価値は、仕様書の番号をテスト項目書やチケットなどの外部に書き写して使う運用があるときに生じる。
  - このプロダクトは、その運用を想定しない。仕様書は常に最新版を参照し、要素の指名は名称とスクリーンショットで行う。
- 番号を安定させる方式（欠番の許容）には、時間とともに悪くなる欠点がある。
  - 削除で生まれる欠番が、読み手に「なぜ番号が飛ぶのか」という違和感を与える。
  - 画面の途中に要素を追加すると、番号が読み順から崩れていく。
- 既存の画面仕様書の運用では、画像 1 枚と構成要素のテーブル 1 つを状態ごとの組として生成し、番号は状態の中で 1 からの連番にするのが慣行である。
  - 画面の全体で番号を通すと、後の状態の画像のバッジが途中の番号から始まり、同じ違和感が状態の方向にも生じる。
- 構成番号を DSL に保存せず生成時に導く案は、成果物にしかない情報を作り、DSL を唯一の元のデータにする原則を壊す。
  - ADR-0011: [YAML DSL を画面操作と画面仕様の唯一の元のデータとする](0011-dsl-as-source-of-truth.md)

## Decision

- 構成番号は、状態の単位で採番する。
  - 各状態が画像とテーブルの組を生成し、番号は常に 1..N の連番で、欠番を作らない。
  - 同じ要素でも、状態が違えば番号は変わりうる。状態の間と版の間の追跡は、永続要素 ID で行う。
- DSL の上の番号の基準は、state ごとの `badges` の順序のリストにする。
  - リストの位置がそのまま構成番号で、要素定義の側に `number` のフィールドは持たない。
  - 成果物は DSL の `badges` をそのまま使い、生成時に番号を計算しない。
- 再採番は、システムが計算して DSL へ書き戻す操作にする。
  - 撮影の結果の bounding box から導いた読み順（左上から右へ、上から下へ）で並べた `badges` のリストを draft として反映し、承認（構成番号の確定）を経て確定済みのデータになる。
  - 同じ撮影の結果と設定からは、常に同じ並びを導く。
- 手での編集も許す。
  - DSL が元のデータなので、利用者は `badges` の並びを直接編集できる。
  - 検証は、参照の解決と重複の禁止だけにする。
- 番号が変わったときは、差分の成果物に番号の対応表（要素 ID を基準にした旧から新）を含める。

読み順の導き方と再採番の手順は [画面要素マッピングの Design Doc](../packages/core-element/DesignDoc.md#読み順の導き方と再採番状態ごと) に、`badges` の書き方は [ワークフロー定義の Design Doc](../packages/core-workflow/DesignDoc.md#要素定義と構成番号の書き方) に、番号の対応表は [変更差分の検知の Design Doc](../packages/core-diff/DesignDoc.md#番号対応表) にある。

## Considered Options

| 選択肢                                                                            | 強み                                                                                                                                                                                  | 弱み                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** 状態の単位で 1..N に採番し、`badges` のリストを基準に読み順で再採番する | 各状態の画像とテーブルが 1..N で完結し、既存の仕様書の読まれ方と一致する。DSL が番号を含めて唯一の元のデータであり続ける。再採番も draft と承認を通るため、番号が知らせずに変わらない | 同じ要素が状態の間と版の間で別の番号になりうる。複数の状態に現れる要素は、各状態の表に重ねて載る。読み順の計算がレイアウトの微小な揺れに左右されうる                                                    |
| 画面の単位で採番する（状態の間で同じ要素は同じ番号）                              | テーブルを画面で 1 つにまとめられ、状態をまたいで番号が安定する                                                                                                                       | 後の状態の画像のバッジが途中の番号から始まる違和感が残り、既存の仕様書の慣行（状態の中で 1..N）と合わない。状態の間で同じ番号にする利点は、番号を外部から参照しない前提では働かず、追跡は要素 ID が担う |
| 番号を安定させ、欠番を許す（永久欠番）                                            | 番号を外部に引用しても、引用が指す要素が変わらない                                                                                                                                    | その運用を想定しない以上、欠番の違和感と途中の挿入による順の崩れのコストだけが残る                                                                                                                      |
| 既定は安定させ、明示の操作でだけ再採番する（ハイブリッド）                        | いつ番号が変わるかを人間が制御できる                                                                                                                                                  | 外部の引用がない前提では守る対象がなく、欠番の管理という状態が増えるだけ                                                                                                                                |
| 構成番号を DSL に保存せず、生成時に導く                                           | 採番の管理が DSL から消え、最も単純                                                                                                                                                   | 成果物にしかない情報が生まれ、画像とテーブルを個別に編集しないという原則と矛盾する。構成番号の確定という承認の対象も失われる                                                                            |

欠番を許す案を採らないことで、欠番を管理する手段（tombstone やカウンタ）も前提ごと要らなくなる。

## Consequences

### Positive

- 各状態の画像とテーブルが 1..N で完結し、既存の仕様書の読まれ方と一致する。
- DSL が番号を含めて唯一の元のデータであり続け、成果物の生成は決定的な写像のままになる。
- `badges` のリストで、番号、表示の順、バッジの対象を 1 か所で表せ、番号の重複のチェックが単純になる。
- 再採番の結果も draft と承認を通るため、番号の変更が知らせずに起きない。

### Negative

- 同じ要素が、状態の間と版の間で別の番号になりうる。
  - 状態をまたいだ要素の言及は、名称と要素 ID で行い、番号の対応表が補助する。
  - 仕様書の番号を外部へ書き写す運用を将来始めるときは、この ADR を見直す必要がある。
- テーブルが状態ごとに分かれ、複数の状態に現れる要素は、各状態の表に重ねて載る。
- 読み順の計算が撮影の結果（幾何の情報）に依存するため、レイアウトの微小な揺れが行のバンドの境界で順の案を変えるおそれがある。
  - 許容の幅の設定と、承認時の手での修正で緩和する。
