# ADR-0010: AI サービスへ送る情報は Snapshot の断片だけとし、設定で明示的に許可したときだけ広げる

## Status

承認

## Context

候補の生成のために、外部の AI サービスへ送ってよい情報の範囲を決める必要がある。  
選択肢は、Snapshot のみ、画像を含む、DOM の情報を含む、の 3 段階である。

送る情報が増えるほど、候補の精度は上がる。  
一方で、対象の Web アプリケーションの画面には、業務データや個人情報が含まれうる。  
送ってよいかは対象のプロダクトのデータ分類に依存し、システムの側で一律に決められない。

## Decision

- 設定を変えない状態で送るのは、Accessibility Snapshot の断片（対象の要素と周りの文脈）と、画面のメタ情報だけにする。
- スクリーンショットの画像と DOM の断片は、対象のプロダクトごとの設定で明示的に許可したときだけ送る。既定は不許可にする。
- パスワードなどの secret の系統のフィールドの値は、設定に関わらず、送る前に常に取り除く。
- 何をどの種別（Snapshot、画像、DOM）で送ったかを実行の記録に残し、後から監査できるようにする。

これらの規則は、送信先を問わず適用する。  
送信先は、利用者のマシン上のエージェントと、外部の AI サービス（AI Port を実装する adapter/ai）の 2 つである。  
MVP で使うのは、提案依頼キューを通してエージェントへ渡す前者だけである。  
ADR-0019: [AI 候補生成をエージェント主導とし adapter/ai を MVP 実装対象外とする](0019-agent-led-ai-suggestions.md)  
ADR-0020: [人間起点の提案依頼を pull 型キューで実現する](0020-suggestion-pull-queue.md)

エージェントへ渡すときも、データは利用者のマシンの外へ出る。  
Claude Code や Codex はローカルで動くプロセスだが、推論はモデルの提供者のサーバーで行う。  
渡した Snapshot、画像、DOM は、そのサーバーへ送られる。  
プロセスがローカルであることと、データがローカルに留まることは別である。

したがって、画像と DOM を送らない既定の不許可は、エージェントへ渡すときも維持する。  
エージェントへ渡すからといって緩めてよい理由は成り立たない。  
送信先によらず維持するのは、次の 3 点。

- 既定の不許可: 画像と DOM は、明示的に許可しない限り送らない。
- secret の系統のフィールドの値の除去: 依頼の内容はエージェントのコンテキストへ入り、そのセッションの履歴に残る。取り除く理由は、送信先ではなく、認証情報を Snapshot を通して広げないことにある。
- 送った種別の記録: 何をどの種別で渡したかを実行の記録に残す。監査できることは、どちらの送信先でも必要である。

送信先によって違うのは、利用者から見た送信先の名前だけで、境界の扱いは変わらない。  
利用者へは、どのモデルの提供者へ渡るかを示す。  
フィルタを適用する位置と、送る内容ごとの既定は [AI 候補生成の Design Doc](../design/features/ai-suggestions/DesignDoc.md#送る情報の境界) にある。

## Considered Options

| 選択肢                                                                                                    | 強み                                                                                                                   | 弱み                                                                                                                     |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **採用:** 既定は Snapshot の断片だけとし、画像と DOM はプロダクトごとの設定で明示的に許可したときだけ送る | データ分類の確認の前でも安全に使い始められる。送ってよいかの判断が、プロダクトの設定を変えるかという明示的な操作になる | 設定を変えない状態では、候補の精度が Snapshot の情報量に制限される。送信の境界のフィルタと監査の記録を実装する必要がある |
| Snapshot のみに固定する                                                                                   | 情報の管理が最も単純になる                                                                                             | 視覚的な手掛かり（アイコンだけのボタンなど）に基づく名称を提案できず、候補の精度の上限が低い。広げる手段がない           |
| 常に画像と DOM を送る                                                                                     | 候補の精度が最大になる                                                                                                 | データ分類が厳しいプロダクトで採用できなくなる。既定を「送る」に置くと、送信の範囲の把握が利用者任せになる               |

## Consequences

### Positive

- 設定を変えない状態で送る情報が最小のため、データ分類の確認の前でも安全に使い始められる。
  - 送ってよいかの判断が、プロダクトの設定を変えるかという明示的な操作になる。
- 送った種別の記録により、AI サービスへ渡った情報の範囲を後から説明できる。
- 規則を送信先から独立させたため、adapter/ai を後から実装しても、送信の境界の設計を作り直さずに済む。

### Negative

- 設定を変えない状態では、候補の精度が Snapshot の情報量に制限される。
- 送信の境界のフィルタと監査の記録の実装にコストがかかる。
