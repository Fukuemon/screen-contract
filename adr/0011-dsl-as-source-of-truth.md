# ADR-0011: YAML DSL を画面操作と画面仕様の唯一の元データにする

## Status

承認

## Context

画面操作と画面仕様の元のデータを、何にするかを決める必要がある。

画面仕様を手で管理すると、画像、構成要素のテーブル、操作のスクリプトが、それぞれ別の元のデータになる。  
その結果、番号の不一致、古い画像の残存、要素定義の重複した割り当てが起きる。  
出典: [PRD の Background](../PRD.md#background)

操作をコマンドの列や一時的なスクリプトとして記録するだけでは、操作の対象、期待状態、構成番号、変更の差分の意味が残らない。

## Decision

- YAML DSL（Screen と Workflow の 2 文書）を、画面操作と画面仕様の唯一の元データにする。
- 注釈画像、Markdown のテーブル、Playwright の POM は、すべて DSL から作る生成物とし、個別に編集できる元のデータにしない。
  - ADR-0006: [元のデータは YAML DSL のまま、Playwright の Page Object コードを生成物として提供する](0006-playwright-pom-output.md)
- 実行系は YAML を直接扱わず、core/workflow が正規化した Workflow IR を使う。

DSL の 2 文書の分け方は ADR-0003 が決めている。  
ADR-0003: [DSL を Screen と Workflow の 2 文書に分離する](0003-dsl-structure.md)

## Considered Options

| 選択肢                                                                   | 強み                                                                                                                                                                         | 弱み                                                                                                                                                          |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** YAML DSL を唯一の元データにし、成果物はすべて DSL から作る     | 画像、テーブル、POM、実行が常に同じ元のデータから作られ、同期のずれが構造的に起きない。Schema による検証と構造化したエラーにより、人間とエージェントの双方が安全に編集できる | 生成物を直接編集しない運用の制約が生まれる。表現力の不足は、その都度 DSL の語彙の拡張で補う必要がある                                                         |
| 成果物（画像、テーブル、スクリプト）をそれぞれ編集できる元のデータにする | —                                                                                                                                                                            | 手で管理している今と同じ同期の問題（番号の不一致、古い成果物の残存）が再び起きる                                                                              |
| Playwright のスクリプトなどのコードを元のデータにする                    | 操作を再現できる                                                                                                                                                             | 期待状態、構成番号、仕様書を文書にする語彙を持たない。非エンジニアの編集と、AI エージェントの安全な部分の編集（Schema の検証で守った draft の編集）ができない |
| 録画（操作の記録）を元のデータにする                                     | —                                                                                                                                                                            | 再現が座標とタイミングに依存して不安定になる。宣言的な期待状態や冪等スキップを表せない                                                                        |

## Consequences

### Positive

- 画像、テーブル、POM、実行が常に同じ元のデータから作られ、同期のずれが構造的に起きない。
- Schema による検証と構造化したエラーにより、人間とエージェントの双方が安全に編集できる。

### Negative

- 生成物を直接編集しない運用の制約が生まれる。
- 表現力の不足は、その都度 DSL の語彙の拡張（バージョンの互換の規則に従う）で補う必要がある。
