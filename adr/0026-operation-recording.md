# ADR-0026: 操作の記録を DSL の draft を書く手段として提供する

## Status

承認

## Context

ブラウザを操作した結果を DSL として残す手段を用意するか、用意するならどう位置づけるかを決める必要がある。  
DSL を書く手段には、人が YAML を手で書く方法と、エージェントが `screen.save_draft` で書く方法がある。  
どちらも、ブラウザを操作した結果を DSL として残せない。

画面仕様を新しく起こす場面では、対象のアプリの操作の列を先に知っている人（その画面を作った開発者、業務の担当者）が、YAML を書けるとは限らない。  
操作はできるが DSL は書けない、という状態が普通にありうる。

ADR-0011 は、「操作をコマンドの列や一時的なスクリプトとして記録するだけでは、操作の対象、期待する状態、構成番号、変更の差分の意味が残らない」ことを、DSL を唯一の元データにする根拠にしている。  
記録そのものは否定していないが、記録の位置づけは決めていない。  
ADR-0011: [YAML DSL を画面操作と画面仕様の唯一の元データにする](0011-dsl-as-source-of-truth.md)

操作モードの間の入力は、すべて Workflow Server の Stream Proxy を通る。  
server は、すべての入力を見ている。  
ADR-0008: [ライブ映像は Workflow Server 経由の Proxy で配信する](0008-stream-proxy.md)

Locator は、Role、Accessible Name、Label、Test ID などの Semantic Locator を優先する。  
出典: [Design Doc の DSL と要素の前提](../design/DesignDoc.md#dsl-と要素の前提)

任意の JavaScript を無制限に実行することは、MVP の範囲の外にする。  
出典: [PRD の Non-Goals](../PRD.md#non-goals)

## Decision

- 操作の記録を、DSL の draft を書く手段の 1 つとして提供する。
  - 記録は確定済みのデータを作らない。出力は draft で、確定済みの DSL への反映は人間の承認を経る。
  - 唯一の元データが DSL であることは変わらない。
  - ADR-0017: [エージェントの操作範囲を draft までとし確定に人間の承認を要する](0017-agent-draft-boundary.md)
- 記録は Workflow Server の側で行う。操作モードの入力は Stream Proxy を通るため、ブラウザへの JS の注入も、agent-browser への依存の追加も要らない。
- 座標をそのまま残さない。各操作について、その時点の Snapshot で座標を解決し、Semantic Locator を持つ要素定義へ対応づける。
  - 既存の要素定義に一致すれば、その `ref` を使う。
  - 一致しなければ、要素候補を作り、新しい要素定義も draft に含める。
  - 一意な Locator へ解決できない場合に限り、`clickPoint` として残し、警告を付ける。
  - 解決の規則は [画面要素マッピング](../packages/core-element/DesignDoc.md#座標からの要素の解決と候補の正規化) にある。
- Expectation は自動で生成しない。操作の後の Snapshot から URL や見えている要素などの候補を出し、採るかどうかは人が決める。
- 記録していることを UI に明示する。知らせずに記録しない。開始と停止は明示の操作にする。
- 記録する操作は、DSL の action の語彙に当たるもの（`open`、`click`、`fill`、`hover`、`scroll`）だけにする。生の入力イベントを残さない。

記録から承認までの流れは [Web UI](../apps/web/DesignDoc.md#操作の記録から-draft-までの流れ) にある。

## Consequences

### Positive

- DSL を書けない利用者でも、画面仕様を起こせる。操作して、Expectation を選び、承認するだけで、確定済みの DSL ができる。
- 記録が Stream Proxy に載るため、agent-browser への依存を増やさない。実装が interface と app に閉じる。
- 記録の出力が draft なので、既存の承認の流れ、差分の表示、エージェントの自己修正がそのまま使える。新しい仕組みを作らない。
- 座標を Locator へ解決してから残すため、記録した DSL がそのまま再現できる資産になる。生の座標の列より長く使える。

### Negative

- 操作モードの意味が増える。これまでは探索のためだけだったが、記録の有無で結果が変わる。UI で明示しないと、利用者が混乱する。
- 一意な Locator へ解決できない操作は `clickPoint` として残り、再現性が下がる。警告は出すが、利用者が無視すれば脆い DSL ができる。
- 記録した steps をどの状態の遷移として扱うかは、機械的に決まらない。人が決める操作が 1 つ増える。
- Expectation を人が選ぶため、記録しただけでは冪等スキップが働かない。選ばずに承認すると、毎回実行されるステップになる。
