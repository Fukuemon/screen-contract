# ADR-0025: 画像差分に pixelmatch と ssim.js を採用する

## Status

承認

## Context

画像差分を、どのライブラリで計算するかを決める必要がある。  
ADR-0007 は、画像差分を「Pixel Diff で粗く拾い、知覚差分で仕分ける」2 段階にすると決めたが、計算に使うライブラリは決めていない。  
ADR-0007: [画像差分は生スクリーンショットを対象に、Pixel Diff → 知覚差分の 2 段階で判定する](0007-visual-diff.md)

判断の優先順位の 1 位は、再現性と決定性である。  
同じ画像の組からいつも同じ判定が出ることを、速さより優先する。  
出典: [Design Doc の判断の優先順位](../design/DesignDoc.md#判断の優先順位)

比べる画像は、1 つの画面の状態ごとのスクリーンショットで、1 回の実行で数枚から数十枚である。  
数千枚を一括で比べる用途ではない。

## Decision

- Pixel Diff は pixelmatch で、知覚差分は ssim.js で計算する。
  - 出典: [pixelmatch](https://github.com/mapbox/pixelmatch)
- 比較のアルゴリズムを自作しない。自作するのは、mask の適用、段階の判定、分類という編成のロジックだけにする。
  - ライブラリが担うのは 2 つの数値を出すところまでで、それをどう解釈するかは自作する。
  - 判定の流れは [変更差分の検知](../packages/core-diff/DesignDoc.md#画像差分の-2-段階判定) にある。
- 速さが問題になってから差し替える。差し替えるのは、次の 2 つをどちらも満たしたときにする。
  - 1 回の差分の検知にかかる時間が、実行の全体の体感を損なう水準に達した。
  - その原因が画像の比較であることを、計測して確かめた。
- 差し替え先の候補は odiff と BlazeDiff にする。どちらもネイティブの実装で、pixelmatch より速い。採るときは、再現性を先に確かめる（同じ入力から同じ判定が出るか、環境の差でぶれないか）。
  - 出典: [odiff](https://github.com/dmtrKovalenko/odiff)
  - 出典: [BlazeDiff](https://github.com/teimurjan/blazediff)

## Consequences

### Positive

- pixelmatch は依存を持たない小さな実装で、生の型付き配列を入力に取る。環境の差で結果がぶれる余地が小さく、再現性の要件と合う。
- どちらも純粋な JavaScript で、ネイティブのバイナリを配布物に持ち込まない。利用者のプラットフォームを選ばない。
- ライブラリの責務を「2 つの数値を出すところまで」に限ったため、差し替えても編成のロジックと判定の語彙は変わらない。

### Negative

- ネイティブの実装より遅い。画像の枚数が大きく増える使い方では、先に頭打ちになる。
- 指標が 2 つのライブラリに分かれるため、依存が 1 つ増える。
