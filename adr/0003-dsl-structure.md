# ADR-0003: DSL を Screen と Workflow の 2 文書に分離する

## Status

承認

## Context

DSL の第一級の構造（1 つのファイルの単位）を決める必要がある。

- 成果物（画面仕様書）は画面の単位で生成する。一方で、画面に到達する操作列は、複数の画面で再利用したい。
- 既存の画面仕様書の運用（実画面の撮影と文書化）では、次の対象が日常的に現れる。これらを表せない DSL では、実画面の文書化が成り立たない。
  - 一覧の行の要素のような、同じセレクタの繰り返し
  - 条件つきでしか表示されない要素
  - ダイアログの単位の切り抜きの撮影
  - 別の文書にした子画面へのリンク
  - canvas の描画のため DOM に現れない操作の対象

## Decision

- DSL を、Screen 文書と Workflow 文書の 2 種類に分ける。
  - Screen は、要素定義、構成番号、画面の状態を持ち、仕様書を生成する単位にする。
  - Workflow は、再利用できる操作列で、Screen の entry から参照する。
- 状態遷移の step は、Screen 文書の中に持つ。
  - モーダルの開閉のような画面の中の状態は、画面の関心事なので、Screen の中で宣言を完結させる。
  - step の語彙は Workflow と同じにし、実行時は同じ IR のステップに正規化する。
- 実画面の文書化に要る語彙を、DSL に持つ。
  - 要素の表示の区分: `badges` に載る要素、`optional`（条件つきの表示）、どちらでもない補助の要素
  - Locator の `index`（複数に一致したときの 1 始まりの序数）と `all`（該当するすべてに同じ番号のバッジ）
  - state の `clip`（撮影する領域）
  - 要素の `child_doc`（別の文書にした子画面への参照）
  - action の `clickPoint`（座標のクリック。canvas など DOM に現れない対象だけに使う）、`hover`、`scroll`
  - 成果物の出力パスの、文書ごとの指定
- 複数の一致は、Semantic Locator での絞り込みを推奨し、`index` は明示的な逃げ道として残す。
- 任意の JS の実行は語彙に入れず、スクロールのような用途は専用の action（`scroll`）で代える。

文書の構造と語彙の規則は [ワークフロー定義の Design Doc](../packages/core-workflow/DesignDoc.md#文書の構造-screen-と-workflow-を分ける) に、`index` と `all` の規則は [画面要素マッピングの Design Doc](../packages/core-element/DesignDoc.md#locator-のモデル) に、出力パスの指定は [仕様成果物の生成の Design Doc](../packages/core-artifact/DesignDoc.md#成果物のファイルの配置) にある。

## Considered Options

| 選択肢                                                                       | 強み                                                                                                                                       | 弱み                                                                                                                                     |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** Screen と Workflow の 2 文書に分け、実画面の文書化に要る語彙を持つ | Screen 文書と画面仕様書が 1 対 1 に対応し、成果物の生成と差分の検知の単位が自明になる。到達手順の変更が Workflow 文書の 1 か所の修正で済む | 文書の間の参照の解決と検証が要る。`index` は DOM の順に依存して脆い                                                                      |
| Screen だけを第一級にする（1 種類）                                          | 文書が 1 種類で単純                                                                                                                        | 複数の画面に共通するログインなどの操作列を、画面ごとに複製することになり、変更がすべての画面に及ぶ                                       |
| Workflow だけを第一級にする                                                  | 画面をまたぐ検証が書きやすい                                                                                                               | 要素定義と構成番号の置き場が操作列の中の状態に結び付き、画面仕様書との対応が間接的になる                                                 |
| 複数の一致（`ambiguous`）を常にエラーにする                                  | —                                                                                                                                          | 一覧やテーブルを含む実画面では、同じ testid の行の要素が普通にあり、エラーにすると文書が書けない                                         |
| 任意の JS の実行（`eval`）を入れる                                           | —                                                                                                                                          | 用途がスクロールなどに限られ、専用の action（`scroll`）で代えられる。任意の JS の実行は [PRD の Non-Goals](../PRD.md#non-goals) に当たる |

## Consequences

### Positive

- Screen 文書と画面仕様書が 1 対 1 に対応し、成果物の生成と差分の検知の単位が自明になる。
- 到達手順の変更が、Workflow 文書の 1 か所の修正で済む。
- 一覧、条件つきの表示、子画面の分割を含む実画面を、語彙の不足で詰まらずに文書化できる。

### Negative

- 文書の間の参照（entry の Workflow の参照、`ref` の要素の参照、`child_doc`）の解決と検証が要る。
  - core/workflow の正規化で吸収する。
- `index` は DOM の順に依存する脆い指定で、乱用すると差分の検知のノイズの元になる。
  - Semantic Locator で絞れない場合の逃げ道と位置づける。
