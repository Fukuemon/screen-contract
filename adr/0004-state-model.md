# ADR-0004: 画面状態を default 根の木で表し、statechart と直交合成を採らない

## Status

承認

## Context

モーダルを開いた状態でのエラートーストのような、ネストした状態をどう表すかを決める必要がある。

DSL が表したいのは、UI の実行時の振る舞いではない。  
文書化する画面状態のカタログと、そこへの到達手順である。

- 成果物（画面仕様書）の生成には、撮影の対象になる、有限で明示的な状態のリストが要る（決定性の要件）。
- 実行は、宣言した手順を線形に再生するモデルであり、任意のタイミングでイベントが飛ぶリアクティブな意味論を必要としない。
- 将来の機能（ノードベースの編集、Playwright の生成、複数の画面をまたぐ検証）を含めて、statechart でなければ表せない要件はない。

比べる状態のモデルは次のとおり。

- statechart: 状態遷移図の拡張。主な拡張は次の 3 つで、UI の実行時の状態管理のエンジンとして動かすのが本来の用途である。XState は statechart を TypeScript で実装した、広く使われるライブラリ。
  - 階層（compound state）: 状態の中に子の状態を持てる。
  - 並行領域（parallel region）: 独立な軸（モーダルの開閉、トーストの有無）を別々の小さな状態機械として並走させ、組み合わせを自動で表す。
  - イベント駆動: イベントが来たら遷移が起きる、というリアクティブな振る舞いを書く。
- フラグメント合成（mixin）: 状態をオーバーレイの断片の合成として宣言する方式（`modal-error = modal-open + toast-error` のような書き方）。
- 木のモデル: 各状態が 1 つの遷移元（`from`）を持ち、根（`default`）からたどる遷移の列が、到達手順そのものになる。

## Decision

- 画面の状態は、`default` を根とする木で宣言する。
  - 各状態は、遷移元の `from` と遷移の手順の `steps` を持つ。
  - ネストは `from` の連鎖の深さで表す（`default → modal-open → modal-error`）。
- 要素は、遷移元の状態から継承する。
  - 要素定義には、初めて現れる状態だけを書き、子孫の状態へ自動で引き継ぐ。
  - 子孫の状態で消える要素は、除外を明示する（`hidden-in`）。
- 操作列の重複は、名前付きの step の断片（`fragments` と `use`）の参照で解消する。
  - 断片は単なる展開で、状態の意味に影響しない。
- statechart（階層、並行領域、イベント駆動）と、フラグメント合成による直交する軸の自動の合成は採らない。

状態の木と継承の規則は、[ワークフロー定義の Design Doc](../packages/core-workflow/DesignDoc.md#状態のモデル-default-を根とする木) にある。

## Considered Options

| 選択肢                                                                  | 強み                                                                                             | 弱み                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **採用:** `default` を根とする木に、step の断片の参照と要素の継承を足す | 状態、仕様書に載る単位、差分の単位が常に一致する。正規化が単純で、同じ文書から常に同じ IR が出る | 直交する軸の組み合わせを手で列挙する必要があり、組み合わせが多い画面では宣言が長くなる                                                                                                                                                                                                     |
| statechart（XState 風）を DSL の状態モデルにする                        | ネストと直交を形式的に表せる。TS のエコシステムに実装の知見も多い                                | 並行領域の状態の空間は軸の積になり、どの組み合わせを仕様書に載せるかの翻訳層が別に要る。イベント駆動の意味論は、線形の再生と冪等スキップの実行モデルと噛み合わない。書き手とエージェントに statechart の意味論（entry/exit、遷移の解決の順）の学習を強い、draft の生成のエラーの面が広がる |
| フラグメント合成で直交する軸を自動で合成する                            | 軸を 1 回ずつ定義して組み合わせられる                                                            | 実際の UI では、断片の到達手順が文脈に依存することが多く（トーストを出す操作がモーダルの中の送信ボタン、など）、断片の steps を機械的につなげても到達手順にならない。結合の規則を定義し始めると、statechart 並みに複雑になる                                                               |
| 木だけで、断片も継承もなし                                              | モデルが最も単純                                                                                 | 深い状態で、操作列と要素の列挙のコピーが増える                                                                                                                                                                                                                                             |

statechart の利点が生きる場面は要件にないため、statechart にはコストだけが残る。  
素の木の欠点は書き味だけで、断片の参照と継承で解消できる。

## Consequences

### Positive

- 状態、仕様書に載る単位、差分の単位が常に一致し、採番、成果物、差分の対応が自明に保たれる。
- 将来のノードベースの編集は、states をノード、`from` をエッジとして、そのまま可視化できる。
- 正規化（遷移の連鎖の平坦化と継承の展開）が単純で、同じ文書から常に同じ IR が出る。

### Negative

- 直交する軸の組み合わせは、手で列挙する必要がある。組み合わせが多い画面では、宣言が長くなる。
- 直交の合成が将来必要になったときは、木の意味論を保ったまま、組み合わせを展開して木のノードを生成する糖衣を後方互換で足す。
  - その時点で ADR を起こす。
