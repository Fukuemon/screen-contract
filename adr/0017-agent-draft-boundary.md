# ADR-0017: エージェントの操作範囲を draft までとし確定に人間の承認を要する

## Status

承認

## Context

エージェントと AI の出力が、管理対象のデータへどこまで書き込めるかを決める必要がある。

本システムは AI ネイティブに設計する。  
エージェントが workflow の定義、実行、要素定義を、人間の操作なしに作って編集できることが、成功の条件である。  
出典: [PRD の Success Metrics](../PRD.md#success-metrics)

一方で、画面仕様書は参照される元のデータである。  
その信頼性（Baseline と構成番号の正しさ）を、AI の出力の正しさに依存させられない。

## Decision

- エージェントと AI の出力が管理対象のデータへ書き込める範囲は draft までとし、確定済みのデータへの反映は人間の承認の後にだけ行う。
- 承認の対象は次の 3 つ。確定済みの DSL の変更も対象に含める。
  - DSL の変更: 確定済みの Screen 文書と Workflow 文書になる。
  - 構成番号: state の `badges`（NumberingPlan）になる。
  - Baseline の更新: 承認した実行結果のセットになる。
- interface の上でも、この境界を守らせる。
  - 確定済みのデータを変更する tool は作らず、エージェントができるのは承認の依頼（`approval.request`）までにする。
- 承認はエージェントの処理を止めず、承認を待つ間もエージェントは他の draft の作業を続けられる。
  - 差し戻しは構造化したコメントで返し、修正と再依頼を繰り返せるようにする。
- 依頼は対象の draft の revision を固定し、承認するときに一致しなければ確定しない。
  - 承認を待つ間の編集が、人間の見ていない差分のまま確定するのを防ぐためである。

draft と確定の規則は [draft と確定](../context/domain/draft-and-confirmation.md) に、承認の依頼の流れは [AI エージェント操作の Design Doc](../packages/agent/DesignDoc.md#承認依頼の流れ) にある。

この境界は、管理対象のデータへの書き込みに限る。  
`run.start`、`run.resume`、`run.rerun_step` は draft の空間に閉じず、対象の Web アプリケーションで実際にクリックと入力を行い、外部に副作用を起こす。  
そのため、draft の安全とは別の制約を置く。

- 対象の限定: 実行してよい origin をプロダクトの設定で列挙し、列挙の外への `open` を拒否する。
- 操作の記録: どの run がどの origin へ何を行ったかを、実行の履歴に残す。
- 破壊的な操作の扱い: 対象のアプリの側の取り消せない操作を、本システムは判別できない。利用者が対象の環境を選ぶ責任を負うことを明示する。

run 系の tool を、人間の承認の対象にしない。  
実行のたびに人間の承認を求めると、エージェントが自律的に再生して失敗を特定するという中核の動線が成り立たないためである。  
代わりに、対象の限定と記録で守る。  
run 系の tool の制約は [AI エージェント操作の Design Doc](../packages/agent/DesignDoc.md#run-系の-tool-は-draft-の空間に閉じない) にある。

## Considered Options

| 選択肢                                                                      | 強み                                                                                                                                                                                                      | 弱み                                                                                                                                                                                                 |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** エージェントの操作範囲を draft までとし、確定に人間の承認を要する | 確定済みのデータの信頼性が人間の承認に結び付き、エージェントの試行錯誤（draft の空間）と切り離される。tool の組み合わせでは確定済みのデータを変えられないことを、interface のテストで機械的に確かめられる | 人間の承認がスループットの上限になる（承認キューの滞留）                                                                                                                                             |
| エージェントにも確定を許す                                                  | —                                                                                                                                                                                                         | 仕様書の信頼性が AI の出力の正しさに直接依存し、誤った Baseline と採番の混入を確定の後にしか発見できない。差分の検知の比較の基準（Baseline）が承認なしに動くと、検知の結果そのものが信頼できなくなる |
| すべての操作に人間の承認を求める                                            | —                                                                                                                                                                                                         | draft の編集まで承認制にすると、エージェントによる自律的な作成、編集、自己修正の繰り返しが成り立たず、AI ネイティブという成功の条件を満たせない                                                      |

## Consequences

### Positive

- 確定済みのデータの信頼性が人間の承認に結び付き、エージェントの試行錯誤（draft の空間）と切り離される。
- tool の組み合わせでは確定済みのデータを変えられないことを、interface のテストで機械的に確かめられる。

### Negative

- 人間の承認がスループットの上限になる（承認キューの滞留）。
  - 承認がエージェントの処理を止めないことと、差分を表示する承認の UI で緩和する。
