# ADR-0018: 再生中の要素定義編集を run 単位の IR version 固定で反映する

## Status

承認

## Context

再生中に編集した要素定義を、いつ反映するかを決める必要がある。  
挙がっている選択肢は、即時に DSL へ反映するか、再生の完了の後にまとめて反映するかの 2 つである。

Web UI は、`screen.save_draft` で編集を即時に draft へ保存することを前提にしている。  
出典: [Web UI の Design Doc](../apps/web/DesignDoc.md)

したがって、論点は draft をいつ書くかではなく、実行中の run が使う評価の基準をいつ差し替えるかである。

core/execution は、同じ Snapshot に対する評価の結果が常に同じであることを、再現性の要にしている。  
テストの観点にも、履歴から run を組み立て直せることを挙げている。  
出典: [冪等実行と再生制御の Design Doc](../packages/core-execution/DesignDoc.md)

要素定義は Locator を通して Expectation の評価に影響するため、run の途中で差し替えると、この 2 つが同時に崩れる。

再生を任意のステップで一時停止し、要素定義を編集した後に、そのステップから再開か再実行ができることは、成功の条件である。  
出典: [PRD の Success Metrics](../PRD.md#success-metrics)

## Decision

- 編集は即時に draft へ保存する。
- 実行中の run は、開始時の Workflow IR のバージョンを固定し、`running` の間は差し替えない。
- pause の間に draft が変わった状態で、`resume` かステップを指定した再実行を求められたら、その時点で新しい IR のバージョンを読み込む。
  - `ir-version-changed` イベントを発行してから、前提の再検証と巻き戻しを行う。
  - ADR-0002: [一時停止をステップ境界とし、pause 中の実ページ操作を許可して再開時に再検証する](0002-pause-semantics.md)
- ExecutionEvent の列にバージョンの境界が残るため、履歴から run を組み立て直せる性質を保てる。

差し替えの契機は、`resume` とステップを指定した再実行の 2 つだけである。  
状態の遷移は [冪等実行と再生制御の Design Doc](../packages/core-execution/DesignDoc.md#実行中は-workflow-ir-のバージョンを固定する) にある。

## Considered Options

| 選択肢                                                                                                        | 強み                                                                                                                                              | 弱み                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** run ごとに開始時の IR のバージョンを固定し、`resume` とステップを指定した再実行のときだけ差し替える | 決定性を保ったまま、止めて直して再開できる。バージョンの境界がイベントの列に残る。差し替えの契機が 2 つに限られ、再検証が起きる条件がはっきりする | `resume` の応答の時間が、編集の有無で変わる                                                                                                                                                                            |
| 完全な即時反映（`save_draft` の時点で、実行中の run の IR を差し替える）                                      | 反映が最も速い                                                                                                                                    | `running` の間にも Expectation の評価の基準が変わり、同じ run の中で決定性が崩れる。ExecutionEvent の列から run を再現できなくなり、core/execution のテストの観点を満たせない                                          |
| 再生の完了の後にまとめて反映する（run の間の編集を UI のバッファにためて、`completed` の後に draft へ書く）   | 決定性が最も高い                                                                                                                                  | 一時停止中に要素定義を編集し、そのステップから再開か再実行するという成功の条件を満たせない。エージェントの `screen.save_draft` はいつでも draft を書けるため、同じ use case で人間とエージェントの振る舞いが二重になる |

## Consequences

### Positive

- 決定性を保ったまま、止めて直して再開できる。
- バージョンの境界がイベントの列に残るため、差分を調べるときに、どの IR のバージョンで評価した結果かを追える。
- 差し替えの契機が 2 つに限られ、再検証が起きる条件がはっきりする。

### Negative

- `resume` の応答の時間が、編集の有無で変わる。
  - 編集があれば、IR の読み込み直しと前提の再検証が入る。
- 操作モードの間と同じく、編集の後の再開でも再検証が起きることを、UI に明示する必要がある。
