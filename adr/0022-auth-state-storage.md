# ADR-0022: 認証状態を暗号化 Storage State で保持し実行時パラメータで指定する

## Status

承認

## Context

認証が要る画面に対応する前に、認証状態の保存の方式を決める必要がある。  
候補は、ブラウザのローカルの Profile、暗号化した Storage State、外部の Secrets の 3 つである。  
認証プロファイルを DSL に持たせるか、実行時のパラメータにするかは、core/workflow の Schema に直接かかわる。  
そのため、実装を始める前に決める必要がある。

決定に関わる制約と事実は次のとおり。

- 認証情報を、DSL、ログ、Snapshot、生成した成果物へ平文で保存しない。
  - 出典: [Design Doc の承認と秘密情報の前提](../design/DesignDoc.md#承認と秘密情報の前提)
- MVP はローカル実行と単一の利用者を前提とし、クラウドでの利用、チームでの利用、CI での実行は範囲の外にする。そのため、外部の Secrets Manager との連携は MVP では要らない。
  - 出典: [PRD の MVP](../PRD.md#mvp)
- 対象のアプリが MFA や SSO を求める可能性は除けない。汎用の製品なので、毎回ログインの手順を実行する方式は既定にできない。
- 同じ DSL と同じ画面の状態からは、同じ成果物を生成する。判断の優先順位の 1 位は、再現性と決定性である。
  - 出典: [Design Doc の Goals](../design/DesignDoc.md#goals)
  - 出典: [Design Doc の判断の優先順位](../design/DesignDoc.md#判断の優先順位)
- ログインする利用者が変わると、画面が変わる。Baseline を認証プロファイルで区別しないと、権限の差による差分が core/diff の検知の結果を占め、検知したい変更が埋もれる。

## Decision

- 認証状態は、Storage State（cookie と localStorage の JSON）として持つ。
  - 実体は、OS のキーストア（macOS Keychain、libsecret、DPAPI）から得た鍵で暗号化して、ローカルに保存する。キーストアには鍵だけを置く。
  - キーストアは小さい secret 向けで、Storage State の JSON をそのまま入れる用途に合わないため、鍵と実体を分ける。
  - 保存の場所と暗号化の契約は [ローカル実行のセキュリティ](../design/features/local-security/DesignDoc.md#暗号化の契約) にある。
- 初回は、人間がブラウザで手動でログインし、その時点の Storage State を取り込む導線を用意する。MFA や SSO がある場合も、初回に人間が通れば、以降は再現できる。
- 認証プロファイルは実行時のパラメータにする。run の開始時に名前で指定し、DSL には書かない。同じ Screen 文書を複数の `authProfile` で実行できる。
  - 認証コンテキストは実行環境の設定であり、画面の仕様ではないと整理する。動的なデータを Fixture、Mock、固定の入力のどれかで再現できるようにする前提と同じ扱いになる。
  - 出典: [Design Doc の実行の前提](../design/DesignDoc.md#実行の前提)
  - ADR-0011: [YAML DSL を画面操作と画面仕様の唯一の元データにする](0011-dsl-as-source-of-truth.md)
- Baseline は `(screen, state, authProfile, generation)` で識別する。`generation` は取り込みの世代で、取り込むたびに 1 つ進める。
  - プロファイルの名前は変えられ、失効したときは取り込み直して中身を差し替える。同じ名前へ別のアカウントの Storage State を入れることもできる。名前だけを識別子にすると、権限の違う結果が同じ Baseline に入る。
  - 古い generation の Baseline は残す。捨てると、取り込み直した直後に「Baseline 未作成」へ戻り、差分の検知が一度使えなくなる。
  - Baseline の構造は [変更差分の検知](../packages/core-diff/DesignDoc.md#baseline-の構造) にある。
- Storage State の失効は、プロファイルごとに宣言した認証の検証条件で判定する。汎用のブラウザの基盤だけでは判定できない。
  - サーバーの側の失効や SSO の期限切れはログイン画面への遷移として現れ、通常の画面の変更や Locator の解決の失敗と見分けがつかない。条件なしに `auth/expired` と決めると、単なる画面の改修を認証のエラーとして報告する。
  - 検証条件は Expectation と同じ語彙で書き、新しい語彙を増やさない。
- Browser Port の `createSession` は認証コンテキストを受け取る。実際の注入は adapter/browser の責務にする。
- Storage State の失効は、機械が読めるコード `auth/expired` を持つ構造化エラーとして返す。
  - 返す条件と Browser Port の契約は [冪等実行と再生制御](../packages/core-execution/DesignDoc.md#browser-port-の契約) にある。

## Considered Options

| 選択肢                                                                                | 強み                                                                                                                                                                                                                                | 弱み                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** 暗号化した Storage State を持ち、認証プロファイルを実行時のパラメータにする | 保存する内容が Storage State の JSON に限られ、何が再現に関わるかを確かめられ、環境の間で移せる。1 つの Screen 文書を複数の権限で実行できる。権限の差による差分が検知の結果に入らない。平文の認証情報がリポジトリと成果物に入らない | 初回の取り込みの導線を実装する。失効したときに取り込み直しを促す導線が要る。OS ごとにキーストアの API が違う                                                                                                           |
| ブラウザの Profile のディレクトリを丸ごと使い回す                                     | 実装がほぼ要らない                                                                                                                                                                                                                  | 中身が不透明で、キャッシュ、拡張機能、履歴など、認証と関係のない状態まで再現の結果に入る。「同じ DSL と同じ画面の状態からは同じ成果物を生成する」と、判断の優先順位の 1 位の再現性と決定性に反する。環境の間で移せない |
| credential を環境変数から渡し、毎回ログインの手順を実行する                           | 保存する状態を持たないため、監査しやすい                                                                                                                                                                                            | run のたびにログインの往復が入って遅い。MFA や SSO のある画面では成り立たず、汎用の既定にできない。補助の手段としては成り立つため、将来の選択肢として残す                                                              |
| 認証プロファイルを DSL（Workflow 文書か Screen 文書）に書く                           | ADR-0011 の「DSL を唯一の元データにする」と最も一貫する                                                                                                                                                                             | 同じ画面を別の権限で見るときに文書が重複する。Screen 文書に書くと、要素 ID の同一性の管理が文書をまたいで複雑になる                                                                                                    |
| 外部の Secrets Manager に置く                                                         | チームでの利用と CI での実行を前提にすれば妥当                                                                                                                                                                                      | どちらも MVP の範囲の外で、ローカルの単一の利用者には過剰である。将来の選択肢にする                                                                                                                                    |

## Consequences

### Positive

- 保存する内容が Storage State の JSON に限られるため、何が再現に関わっているかを確かめられ、環境の間で移せる。
- 認証プロファイルを実行時のパラメータにしたので、1 つの Screen 文書を複数の権限で実行して差分を見る使い方を、文書を複製せずに書ける。
- Baseline を認証プロファイルで区別するため、権限の差による差分が、ノイズとして検知の結果に入らない。
- 平文の認証情報が、リポジトリと生成した成果物に入らない。

### Negative

- 初回の取り込みの導線を実装する必要がある。ブラウザの Profile を使い回す案にはない手間である。
- Storage State には期限がある。失効すると run が失敗するため、`auth/expired` を検知して取り込み直しを促す導線が要る。
- OS ごとにキーストアの API が違うため、3 系統の実装か、抽象化のライブラリの採用が要る。
