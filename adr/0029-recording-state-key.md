# ADR-0029: 記録中の画面状態を URL の代理鍵で識別する

## 状態

承認

## 決定日

2026-08-26

## 背景

- [adr/0005](0005-badge-renumbering.md) は構成番号を**状態単位**で採番すると定める。各状態の画像とテーブルが 1..N で自己完結し、状態をまたいで連番にしない。
- [adr/0004](0004-screen-state-model.md) は画面状態を `default` を根とする木のノードと定め、「状態 = 仕様書に載る単位 = 差分の単位」とする。状態には DSL 上の **state 名**がある。
- ところが **live viewport で記録している最中には state 名がまだ無い**。state 名は Screen 文書が確定して初めて決まり、記録はその文書を起こすための操作である。鍵が無いまま採番すると、番号を 1 本の列で持つことになる。
- 実際にそうなっていた。別の画面へ移っても前の画面の番号が残り、**居ない要素へ番号を振ったまま**になる。利用者から不具合として報告された。

## 決定

- **記録中は URL (`origin` + `pathname`) を画面状態の代理鍵とする。** 構成番号と要素定義はこの鍵ごとに持つ。
- `query` と `fragment` は鍵から落とす。落とさないと、同じ画面を指す URL が別の状態として増え、番号を振り直す先が分からなくなる。
- **代理鍵であることを写しの名前で示す。** `ViewportSnapshot` の項目名は `stateId` とし、値が URL であることに依存した名前 (`stateUrl`) を使わない。state 名が決まった段では、鍵の作り方だけを差し替える。
- 解釈できない URL はそのまま鍵にする。落とすと、番号が黙ってどこかの画面へ紛れ込む。

## 代替案

- **state 名が決まるまで採番できないことにする**: ADR-0004 に忠実で、代理鍵という概念が要らない。しかし記録の目的が「番号を振った画面仕様書を起こすこと」であるため、採番できない記録には価値が無い。却下。
- **URL + 可視要素の集合を鍵にする**: 同じ URL 上のモーダル開閉を別の状態として扱える。ADR-0004 の「状態 = 仕様書に載る単位」に最も近い。しかし可視要素は読み込みの途中でも変わるため、**鍵が操作と無関係に増える**。番号の帳簿が意図せず分裂する側の失敗は、統合される側より気付きにくい。skeleton の範囲では採らない。
- **利用者に状態名を付けさせる**: 曖昧さが無い。しかし記録のたびに命名を求めることになり、記録の手数が増える。番号を振る前に名前を決めさせる順序も、実際の作業と合わない。却下。

## 影響

### 良い影響

- 別の画面へ移っても番号を引き継がない。往復しても、元の画面へ戻れば番号も戻る。
- 鍵の作り方が 1 つの関数 (`stateKeyOf`) に閉じる。state 名へ移すときに直す場所が 1 箇所で済む。

### 悪い影響 / トレードオフ

- **同じ URL 上のモーダル開閉を区別できない。** `default` と `modal-open` が 1 つの帳簿へ潰れる。モーダルの中の要素へ番号を振ると、モーダルを閉じた画面の番号として残る。
- 逆に、同じ状態が URL 違いで分裂する。`/items/1` と `/items/2` が同じ画面でも別の帳簿になる。
- どちらも state 名へ移した段で解消するが、**移すまでの間は利用者が気付ける必要がある。** 番号のパネルへ、いま採番している画面を常時表示する。

### 影響範囲

- 対象モジュール / package: app (viewport) / api / web
