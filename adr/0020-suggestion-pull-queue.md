# ADR-0020: 人間起点の提案依頼を pull 型キューで実現する

## Status

承認

## Context

Web UI だけを操作している利用者が、AI の補完を受け取る手段を決める必要がある。  
AI 候補生成の主な動線はエージェント自身の推論で、エージェントが起点になる。  
本システムは LLM の credential を持たないため、サーバーから AI サービスを呼んで補完することはできない。  
ADR-0019: [AI 候補生成をエージェント主導とし adapter/ai を MVP 実装対象外とする](0019-agent-led-ai-suggestions.md)

agent interface は MCP と App Server 型 JSON-RPC の両方を提供する。  
App Server 型 JSON-RPC は双方向のストリームを持つため、サーバーからエージェントへ要求を送る余地がある。  
ADR-0016: [agent interface に MCP と App Server 型 JSON-RPC の両方を採用する](0016-dual-agent-protocol.md)

MCP は、現行の仕様でサーバーからクライアントへの任意の要求を持たない。  
sampling は deprecated で、push は `subscriptions/listen` のリストの変更とリソースの購読に限られる。  
そのため、push 型は 2 つのプロトコルの間で非対称になる。

## Decision

人間を起点とする提案依頼を、pull 型のキューで実現する。  
app 層に依頼のキューを置き、agent interface に読み取り用の `suggestion.list` と応答用の `suggestion.respond` を公開する。  
エージェントが依頼を取りに来て、応答を draft として書き戻す。  
キューのデータモデルと状態遷移は [AI 候補生成](../design/features/ai-suggestions/DesignDoc.md#提案依頼キュー) にある。

サーバーからエージェントへ要求を push する方式は採らない。

依頼を特定のエージェントへ排他的に割り当てない。  
複数のエージェントが同じ依頼に応答した場合、応答は複数の draft として並び、人間が選ぶ。  
draft は、もともと複数が並ぶ設計である。  
ADR-0017: [エージェントの操作範囲を draft までとし確定に人間の承認を要する](0017-agent-draft-boundary.md)

依頼が応答されないまま期限を過ぎたら `expired` にし、Web UI は手動で名付ける導線へ戻す。  
これで、ADR-0019 の「AI なしでも要素マッピングが完結する」要件を、提案依頼の仕組みが壊さないようにする。

未処理の依頼のリストを、購読できるリソースとしても公開する。  
契約は pull のままで、待ち時間だけを縮める。  
通知は見に来る合図であり、依頼の割り当てではない。  
通知を取りこぼしても `suggestion.list` のポーリングで追いつけるため、購読は最適化であり、前提にしない。  
購読のやりとりは [AI エージェント操作](../packages/agent/DesignDoc.md#待ち時間を縮める購読) にある。

App Server 型 JSON-RPC はロングポーリングで待てるため、購読は要らない。  
ADR-0016: [agent interface に MCP と App Server 型 JSON-RPC の両方を採用する](0016-dual-agent-protocol.md)

## Verification

MCP の仕様（2026-07-28）で、リソースの購読が使えることを確かめた。  
未処理の依頼のリストを 1 つのリソースとして公開し、依頼が積まれたときにサーバーが更新を通知できる。

## Consequences

### Positive

- Web UI の利用者も AI の補完を受け取れる。その間も、本システムは LLM の credential を持たない。
- `approval.request` と `approval.status`（エージェントから人間への依頼）と対称な語彙になり、agent interface の tool の語彙がそろう。
- エージェントに依存しない。接続するエージェントの種類を問わず動く。
- エージェントが利用者の側で動く構成を保つため、サーバーを将来リモートにしても成り立つ。

### Negative

- エージェントが `suggestion.list` を呼びに来ない限り、依頼は処理されない。応答までの時間が保証されない。緩和には次の 2 つを想定する。
  - 利用者へ配る skill に「作業中は定期的に `suggestion.list` を確かめる」と書く。
  - App Server 型 JSON-RPC では、`suggestion.list` をロングポーリングで待たせる。
- 複数のエージェントが接続している場合、同じ依頼に対して応答が重なる。MVP の想定（単一の利用者と単一のエージェント）では実害がないが、承認のキューに並ぶ draft は増える。
